● git reset --hard origin/main forces the code checkout on the droplet to become an exact copy of what's on GitHub's main branch. It runs right after git fetch origin main
  (which downloads the latest commits into the local origin/main pointer but doesn't change your files yet).

  Specifically, reset --hard does three things at once:

  1. Moves the branch pointer (HEAD) to the commit origin/main points to.
  2. Resets the staging area to match that commit.
  3. --hard = overwrites the working tree — every tracked file on the server is made identical to that commit. Any in-place edits to tracked files on the droplet are discarded,
   and any local commits the server had that aren't on origin/main are dropped.

  Why a deploy uses it instead of git pull

  git pull does a merge/fast-forward, which can fail or conflict if the server's files diverged from the remote. reset --hard sidesteps that — it guarantees the server matches
  GitHub byte-for-byte, every time, no conflict prompts. The principle: GitHub is the single source of truth; the server is disposable.

  What's safe (this is the important part)

  reset --hard only touches tracked files. It does not delete untracked or git-ignored files, so these survive untouched:
  - backend/.env — your DATABASE_URL, JWT secret, etc. ✅ (it's gitignored)
  - node_modules/, dist/, backend/public/ build output ✅
  - Any uploaded files / local data ✅

  The one risk

  If someone had hand-edited a tracked file directly on the server (a hotfix typed into the box, not committed), reset --hard wipes it. That's intentional for deploys — but
  it's the reason you should never edit code directly on the droplet; change it in git and redeploy.

  So in the deploy flow it just means: "throw away whatever code is on the server and lay down exactly what's on main" — then the script applies migrations, builds, and
  restarts on top of that clean code.
